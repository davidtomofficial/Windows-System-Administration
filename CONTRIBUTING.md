# Contribution and review rules

Read [LICENSE.md](LICENSE.md) first. Request explicit permission before using or contributing covered original software outside an existing grant. Do not submit material whose ownership or license you cannot establish. Keep the applicable permission, license and provenance clear before submitting a change.

## Submission rights and existing terms

Identify the source, author or rights holder, applicable license and any modifications for contributed code, documentation and assets. Preserve existing copyright, license and attribution notices. If the right to submit material under the applicable terms is unclear, resolve that question before it is incorporated. Repository visibility and attribution alone do not establish ownership or unrestricted reuse rights.

[GitHub Terms of Service, section D.6](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service#6-contributions-under-repository-license) provides that content added to a repository containing a license notice is contributed under the same terms, unless a separate agreement provides different terms. Apply that rule to the actual applicable license; the current rights-reservation notice does not replace prior GPL grants or third-party terms. GitHub's terms do not establish that David Tom owns every contribution.

No contributor license agreement (CLA), Developer Certificate of Origin (DCO) sign-off requirement or copyright-assignment agreement is established by this file. Do not describe a pull request, issue, commit sign-off or review approval as an executed separate agreement. Identify any actual separate agreement and its scope when one applies. See [agreement status](Docs/AGREEMENT-STATUS.md) and [license scope and historical grants](Docs/LICENSING.md).

## Review practice

Use small reviewed changes, synthetic fixtures and exact source/test evidence. Keep historical attribution and task IDs. Do not commit real endpoint reports, credentials, tenant/customer data, vendor installers or private configuration. State whether work is implemented, tested, deployed or merely proposed.

Do not bypass execution policy, suppress tests to make CI green, change unrelated drafts, rewrite history, enable website hosting or run security labs as part of ordinary repository work. Use the [work-agent handoff](Docs/WORK-AGENT-HANDOFF.md) and [repository review TODO](Docs/REPOSITORY-REVIEW-TODO.md) for the approved scope.
